Từ khi nhận một task mới đến lúc kiểm tra, tích hợp và merge code.

Workspace Manager giúp mỗi agent làm việc trong source riêng, chạy môi trường test riêng khi cần, sau đó tích hợp và kiểm tra trước khi đưa code vào main.

BẮT ĐẦU NHANH

Bắt đầu nhanh

Toàn bộ vòng đời một task, từ lúc tạo tới lúc sandbox được dọn dẹp:

  1. Add to BacklogMột ý định công việc — chưa tạo branch/worktree/sandbox.
  2. Select for DevelopmentBACKLOG → PREPARE, vẫn chưa cấp resource.
  3. Viết Implementation Brief + Generate PromptGOAL/REQUIREMENTS/ACCEPTANCE_CRITERIA... rồi sinh AGENT PROMPT để review trước.
  4. Create Agent WorkspaceChọn repository, agent, role, sandbox — lúc này mới tạo branch/worktree.
  5. Mở Claude / Codex (desktop hoặc Open in Web)Agent sửa code trong source riêng.
  6. Builder reportWHAT_CHANGED/FILES_CHANGED/TESTS_RUN/HOW_TO_VERIFY — coi như Mark Ready.
  7. Start ReviewChọn reviewer agent, prompt review tự sinh từ brief + builder report.
  8. REVIEW_PASS (hoặc Start Tester nếu risk HIGH)FIX_REQUIRED trả task về Development.
  9. Create IntegrationGhép các Agent Workspace đã sẵn sàng lại để kiểm tra chung.
  10. READY_FOR_MAINĐủ điều kiện để mở Pull Request.
  11. PR / CI / MergeTạo GitHub Pull Request, chờ CI PASS, merge trên GitHub.
  12. Close TaskSau khi MERGED — sandbox vào lịch cleanup.
BƯỚC 1

Khi có bug hoặc task mới

Vào Tasks → New Task. Form New Task tạo Task + Agent Workspace đầu tiên trong cùng một lần bấm — bạn không cần tự tạo worktree riêng.

  • Task title
  • Description (không bắt buộc)
  • Repository / Agent / Role / Base branch / Sandbox cho Agent Workspace đầu tiên
Ví dụ

Title: Fix lỗi kiosk không gửi được sản lượng

Repository: esp-kiosk · Agent: Claude · Role: Firmware · Sandbox: Auto

Task nhiều repo? Bấm + Add another Agent Workspace để khai báo thêm Agent Workspace (repo/agent/role khác) ngay trong lúc tạo Task — xem mục Task nhiều repository.

Workspace Manager sẽ tự tạo branch và worktree riêng cho từng agent. Nếu một Agent Workspace tạo lỗi (ví dụ repo chưa đăng ký), Task và các Agent Workspace đã tạo thành công vẫn giữ nguyên — lỗi hiển thị rõ, không tự rollback.

Cần một Task rỗng để lên kế hoạch trước? Dùng mục "Advanced: Task rỗng (DRAFT)" — Task này chưa có Agent Workspace nào cho tới khi bạn thêm.

Tiếp theo: Xem Task vừa tạo, mở agent để bắt đầu code.
Đi tới Tasks
PHÂN BIỆT

Task khác Worktree thế nào?

Bạn quản lý Task — Workspace Manager tự lo phần Git bên dưới.

TaskCông việc cần hoàn thành. Có thể trải nhiều repo, nhiều Agent Workspace.
Agent WorkspaceNơi một agent làm một phần của Task — sở hữu đúng một branch/worktree/sandbox.
WorktreeCơ chế Git bên dưới. Bạn không cần tự cd vào đây.
SandboxMôi trường chạy/test cho một Agent Workspace hoặc cho Integration.
TASK · AGENT WORKSPACE(S) · INTEGRATION · VERIFICATION · MERGE
AGENT WORKSPACE

Agent Workspace là gì?

Mỗi Agent Workspace là một vùng source riêng cho một agent. Claude sửa task A sẽ không sửa trực tiếp vào source đang dùng bởi Codex hoặc main.

Claude
→ branch riêng
→ worktree riêng
Codex
→ branch riêng
→ worktree riêng
MỘT AGENT WORKSPACE = MỘT REPOSITORY + MỘT BRANCH + MỘT WORKTREE

Bạn không cần tự cd tới thư mục worktree. Bấm Open Claude / Open Codex để Workspace Manager mở đúng nơi (xem mục kế tiếp).

DESKTOP LAUNCHER

Bắt đầu cho agent sửa code

Trong Agent Workspace có các nút:

Open Claude / Open CodexMở terminal ngay tại worktree của task, chạy sẵn agent CLI.
Open TerminalChỉ mở terminal tại đúng worktree, không tự chạy agent.
Copy PathSao chép đường dẫn worktree nếu bạn muốn tự mở bằng công cụ khác.
Mark ReadyBáo workspace đã sẵn sàng để tích hợp, sau khi đã commit.
Ví dụ

Nếu workspace thuộc Claude: bấm Open Claude. Terminal sẽ mở ngay tại đúng worktree của task.

Không nên mở Claude/Codex ở source main/shared rồi yêu cầu sửa cùng task.
Cảnh báo mức quyền cao

Claude có thể được mở bằng claude --dangerously-skip-permissions. Codex có thể được mở bằng codex --yolo. Các mode này cho agent quyền thao tác mạnh trong worktree. Chỉ dùng vì source của task đã được cô lập — không dùng các mode này trên main hoặc source dùng chung.

Sandbox dùng để làm gì?

Worktree= cô lập source code

Claude Worktree A

Nếu hai agent cùng chạy backend/database trên một môi trường chung, test có thể đạp dữ liệu hoặc port của nhau. Sandbox tạo môi trường test riêng cho từng task — mỗi sandbox có port và database riêng.

CHỌN SANDBOX

Chọn Sandbox thế nào?

AutoKhuyên dùng. Workspace Manager chọn profile theo cấu hình của project.
NoneKhông tạo môi trường runtime. Dùng cho docs, code analysis, thay đổi không cần chạy app.
BackendTạo backend + database cần thiết cho task.
Full StackTạo môi trường đầy đủ: backend, frontend, QA hoặc service phụ.
Hardware / KioskDùng khi ESP/Kiosk cần kết nối tới backend sandbox qua LAN.
Shared DevDùng môi trường development dùng chung, không hoàn toàn isolated. Chỉ dùng khi biết rõ task không ảnh hưởng môi trường khác.
Nếu không chắc, chọn Auto.

HOÀN THÀNH

Khi agent sửa xong

Agent nên:

  1. Sửa code
  2. Chạy test
  3. Review diff
  4. Commit
  5. Báo kết quả

Sau đó bạn bấm Mark Ready.

Mark Ready có nghĩa:

Workspace này đã sẵn sàng để đưa sang bước Integration. Không có nghĩa là code đã vào main.

Tiếp theo: Tạo Integration để kiểm tra code đã ghép.
Đi tới Tasks
READY ≠ XONG

Agent báo READY rồi thì làm gì?

READY ≠ task hoàn tất. READY chỉ có nghĩa agent coi source đã xong, sẵn sàng để verify/tích hợp — chưa test, chưa verify thủ công, chưa tích hợp, chưa sẵn sàng lên main.
READY
→ Sandbox
→ Test
→ Manual Check
→ Integration
→ READY_FOR_MAIN

Agent Workspace và Task Detail đều có khối trạng thái riêng cho từng bước (Agent code / Sandbox / Automated tests / Manual verification / Integration / READY_FOR_MAIN) và một khối Bước tiếp theo tính tự động theo trạng thái hiện tại — không đoán, không dùng AI, chỉ theo luật cố định.

Nếu agent đã báo cáo theo mẫu Agent Completion Report (templates/agent-completion-report.md: WORK_STATUS/WHAT_CHANGED/HOW_TO_VERIFY/EXPECTED_RESULT/TEST_DATA/RISKS), phần Cách kiểm tra trên trang sẽ hiện đúng nội dung đó — nếu agent chưa báo cáo, trang sẽ nói thật: "Agent chưa cung cấp hướng dẫn kiểm tra." thay vì tự bịa ra các bước.

INTEGRATION AGENT

Integration Agent làm gì?

Integration Agent không phải agent viết feature chính. Nó chịu trách nhiệm:

  • Xem diff của các branch
  • Kiểm tra source nào thay đổi
  • Merge
  • Phát hiện conflict
  • Xử lý conflict đơn giản
  • Chạy test
  • Kiểm tra sandbox
  • Báo READY_FOR_MAIN hay FIX_REQUIRED

Bấm Open Integrator để mở Claude/Codex tại môi trường Integration.

CONFLICT

Nếu merge bị conflict

  • Conflict đơn giản: Integration Agent có thể tự xử lý.
  • Conflict logic/API/schema: Integration Agent phải phân tích trước khi sửa.
  • Nếu không chắc: status = FIX_REQUIRED và trả việc về Agent Workspace phù hợp.
Không cần sửa lỗi của Claude trên integration branch nếu lỗi đó thực sự thuộc branch Claude. Quay lại Claude Workspace → sửa → commit mới → Merge Latest.

CẢNH BÁO

SOURCE STALE nghĩa là gì?

Sandbox đã được tạo từ commit cũ, nhưng branch đã có commit mới.

Ví dụ

Sandbox: abc123 · Current: abc999

Hành động: bấm Rebuild Sandbox.

Kết quả test cũ không còn đủ để xác nhận code mới.
SO SÁNH

Restart hay Rebuild?

RestartChạy lại cùng sandbox/source hiện có.

Dùng khi: service treo, backend cần restart.
RebuildBuild lại sandbox từ source hiện tại (commit mới nhất).

Dùng khi: agent vừa commit code mới, Docker image cần build lại, source đang SOURCE STALE.
TRA CỨU

Trạng thái Sandbox

Trạng tháiÝ nghĩa
RUNNINGSandbox đang chạy và health check PASS.
UNHEALTHYContainer có thể đang chạy nhưng ứng dụng chưa healthy.
STOPPEDSandbox đã dừng nhưng data vẫn còn.

Xem task đã hoàn thiện tới đâu

TEST READINESS

Task này test được chưa?

Task Detail trả lời trực tiếp câu hỏi này bằng phần Test Readiness, suy ra từ trạng thái thật (không phải một cờ lưu riêng):

  • ✓ Backend workspace READY
  • ✓ Frontend workspace READY
  • ✓ Sandbox HEALTHY

Full integration test: YES / NO / PARTIAL

NOCòn workspace CODING, sandbox cần mà chưa có/unhealthy/SOURCE STALE, hoặc còn conflict chưa xử lý.
PARTIALMột số Agent Workspace test được riêng, nhưng full integration test chưa sẵn sàng.
YESMọi Agent Workspace cần thiết đã READY, runtime cần thiết sẵn sàng, source đang current.

Task Detail cũng phân biệt rõ Workspace Tests (test riêng branch một agent) và Integration Tests (test trạng thái đã ghép) — không coi Task là "đã test đầy đủ" chỉ vì từng workspace test riêng đã PASS.

KANBAN

Kanban dùng thế nào?

Kanban hiển thị vòng đời Task theo cột — dùng khi bạn muốn nhìn nhanh nhiều task đang ở đâu. Tasks (List) cùng dữ liệu, dạng bảng, tiện lọc/tìm kiếm. Board và List giữ nguyên bộ lọc khi chuyển qua lại.

CộtÝ nghĩa
BACKLOGTask chưa có Agent Workspace
DEVELOPMENTAgent đang code
TESTMọi Agent Workspace đã READY, chưa Integration
FIX REQUIREDCó test/verify FAIL hoặc merge conflict
INTEGRATIONĐã Create Integration, đang ghép/test
READY FOR MAINĐủ điều kiện mở Pull Request
DONEĐã merge hoặc huỷ
Cột được tính tự động từ trạng thái Agent Workspace/Sandbox/Test/Integration thật — không kéo-thả tuỳ ý để bỏ qua điều kiện.
READINESS

READY_FOR_MAIN nghĩa là gì?

Task đã qua các bước kiểm tra cần thiết và có thể đưa sang PR/CI.

  • Các source branch đã merge vào Integration
  • Không còn conflict
  • Integration sandbox healthy
  • Required tests PASS
  • Source chưa thay đổi sau lần test
  • Verified commit đúng với HEAD hiện tại
Với task nhiều repo: tất cả repository tham gia phải đạt trạng thái tương ứng.
READY_FOR_MAIN không có nghĩa là đã merge main.

Nó chỉ có nghĩa integration đã đủ điều kiện để tạo Pull Request.

BƯỚC CUỐI

Sau READY_FOR_MAIN

Push integration branch→Tạo GitHub Pull Request→GitHub CI→CI PASS→Merge main
git push -u origin integration/session-management
Workspace Manager không bypass GitHub CI và không tự merge main. Tạo Pull Request và merge trên GitHub là thao tác thủ công ngoài Workspace Manager — hiện tại phiên bản này chưa tự động tạo PR hay tự merge.
Tiếp theo: Push branch và tạo Pull Request.
SAU MERGE

Sau khi task merge thành công

Sandbox không bị xóa ngay.

MERGED
↓ Retention
↓ mặc định 24 giờ
↓ Auto Cleanup

Giữ lại một thời gian để còn xem logs, runtime, DB sandbox, evidence — nếu vừa merge xong mà phát hiện vấn đề.

Cleanup xoá: containers, sandbox network, sandbox volumes, generated runtime env, port reservations.

Cleanup giữ lại: task history, source commits, test results, audit, integration report.

Nút điều khiển cleanup

Extend 24hDời thời điểm cleanup thêm 24 giờ.
Cleanup NowDọn ngay lập tức. Chỉ xoá runtime/data của sandbox, không xoá source code.
Huỷ lịch cleanupBấm Start trên sandbox đang Cleanup Pending — sandbox chạy lại và tự động ra khỏi hàng chờ cleanup.
SO SÁNH

Stop khác Cleanup thế nào?

StopDừng ứng dụng · giữ data · giữ port · có thể Start lại.
CleanupXóa runtime sandbox · xóa sandbox-owned data/volume · release port · metadata/evidence vẫn còn.
REPOSITORIES

Repositories

Workspace Manager không cần nằm trong repository được quản lý — repo có thể ở bất kỳ đâu dưới workspace root đã cấu hình.

Configured root{{settings.root}}

Vào Repositories để Register repo mới, hoặc chọn từ danh sách Discovered. Danh sách Discovered luôn tự làm mới mỗi khi bạn mở lại trang — nếu vừa thêm hoặc di chuyển một repo, chỉ cần tải lại trang Repositories.

KHÔNG CÓ SANDBOX

Project không khai báo Sandbox

Nếu Task Detail hiện dòng:

Sandbox is not configured for this repository.

Agent vẫn có thể làm việc bình thường bằng worktree — Sandbox chỉ là tính năng tuỳ chọn. Muốn có sandbox tự động, project cần khai báo sandbox: trong PROJECT.yaml của repository đó (phần kỹ thuật này do người phụ trách repo cấu hình, không bắt buộc với mọi project).

  6. Ghi Hardware Test resultPASS / FAIL / NOT_RUN, nếu project yêu cầu.
Không dùng Production endpoint để test task. Việc flash thiết bị thật vẫn là thao tác thủ công — Workspace Manager chưa tự động flash firmware.

KHI CÓ LỖI

Khi test fail

Nếu lỗi thuộc một Agent Workspace: quay lại workspace đó → Open Claude/Codex → sửa → commit → Mark Ready → Integration Merge Latest → retest.

Nếu là conflict chỉ phát sinh khi tích hợp (không thuộc riêng branch nào): Integration Agent có thể tạo integration-only fix.

Nếu sandbox fail

  1. Xem Status
  2. Mở Logs
  3. Xem Health
  4. Retry / RebuildBấm Start để thử lại, hoặc Rebuild nếu source đã đổi.
Sandbox fail không đồng nghĩa source worktree bị mất — code của agent vẫn còn nguyên, chỉ môi trường chạy thử bị lỗi.

SANDBOX_CAPACITY_FULL

POLICY

LOW/NORMAL/HIGH khác nhau thế nào?

Mỗi Task chọn một risk profile ở bước viết Implementation Brief — quyết định những gate nào bắt buộc trước khi Integration:

LOWBuilder → Review. Bỏ qua QA.

HIGHBuilder → Review → QA → Integration. Bắt buộc QA trước khi ghép.
Không có một luồng cứng cho mọi Task — Kanban tự thêm/bớt cột QA tuỳ risk profile.
WEB TERMINAL

Web terminal dùng thế nào?

Mỗi Agent Workspace có thể mở một AgentSession — một PTY thật (không phải log giả) chạy đúng agent CLI (Claude/Codex) trong đúng worktree, xem trực tiếp từ trình duyệt qua WebSocket.

  1. Open in WebTrên Agent Workspace hoặc Task Detail.
  2. Xem output trực tiếpxterm.js render đúng những gì terminal thật in ra.
  3. Gõ lệnh nếu ở chế độ INTERACTIVEVIEW_ONLY chỉ xem, không gửi được phím.
  4. Stop khi xongDừng hẳn tiến trình, không chỉ đóng tab.

Vào Live Agents để xem mọi session đang chạy trên máy này (Task / Agent / Workspace / State / Sandbox / Last activity).

An toàn lệnh: trình duyệt chỉ gửi được workspace_id + chế độ xem — không gửi được cwd, executable, hay flags. Backend luôn tự suy ra lệnh thật từ danh sách agent đã cấu hình sẵn (giống launcher desktop).
Nếu server Workspace Manager khởi động lại, mọi PTY đang chạy trước đó thực sự đã mất — trạng thái sẽ hiện FAILED trung thực, không báo nhầm là RUNNING.
BẢO MẬT

Remote Access Security

Không expose Web Terminal ra Internet công khai, không xác thực. Terminal PTY tương tác có thể thực thi lệnh thật trong worktree thật.

Nếu cần truy cập từ xa, dùng một trong các phương án đã xác thực:

  • Tailscale (mạng riêng, xác thực thiết bị)
  • Cloudflare Access (xác thực trước khi tới app)
  • SSH tunnel / port-forward tới localhost

Workspace Manager tự nó chỉ bind 127.0.0.1 — đây là lớp bảo vệ đầu tiên; lớp xác thực remote access là trách nhiệm của người vận hành.

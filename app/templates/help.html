WIZARD

Task Detail hoạt động như một wizard

Mở một Task, bạn luôn thấy đúng một bước hiện tại — không cần tự hỏi "giờ phải bấm gì tiếp". Toàn bộ chi tiết kỹ thuật (Agent Workspace, Sandbox, Review, QA, Integration...) vẫn còn nguyên, chỉ nằm trong "Xem tất cả chi tiết kỹ thuật" ở cuối trang cho ai cần.

START AGENT

Start Agent làm gì?

Start Agent (nút Start Claude/Start Codex, hoặc Resume Agent) làm hết trong một lần bấm:

  1. Mở agent CLITạo/kết nối AgentSession thật (real PTY), đúng worktree của Task.
  2. Chờ agent sẵn sàngĐợi CLI khởi động xong (bounded wait — tối đa vài giây), không gõ mù ngay khi CLI có thể còn đang vẽ màn hình.
  3. Tự động gửi Task promptPrompt đã sinh sẵn (Task + role + rule repo) được gửi thẳng vào agent — bạn không cần copy/paste thủ công.
  4. Agent bắt đầu làm việcTrạng thái hiển thị: Agent RUNNING + Prompt: DELIVERED.

Nếu gửi prompt thất bại (CLI chưa kịp sẵn sàng, hoặc lỗi khác), màn hình hiện PROMPT NOT DELIVERED kèm nút [Send Task to Codex/Claude] để thử lại — đây là hành động khôi phục ngoại lệ, không phải luồng bình thường.

Resume Agent (khi Review yêu cầu sửa, hoặc agent thoát mà chưa báo cáo) thông minh: nếu agent đang chạy và đã nhận prompt rồi thì KHÔNG gửi lại (tránh gửi trùng); nếu Review trả FIX_REQUIRED thì gửi prompt sửa lỗi (task gốc + nhận xét review), không phải prompt cũ.

SANDBOX

Reset Sandbox Data dùng khi nào?

Reset Sandbox Data (trong Sandbox Detail → Advanced/Danger) xoá database + dữ liệu runtime riêng của sandbox đó, rồi khởi tạo lại từ đúng source hiện tại — port và identity của sandbox được giữ nguyên, source code không bị ảnh hưởng.

Dùng khi cần test hành vi từ trạng thái sạch:

  • Mật khẩu/tài khoản mặc định (default credentials)
  • Hành vi lần chạy đầu (first-run/onboarding)
  • Seed data, migration
Đây là thao tác phá huỷ dữ liệu (destructive) — luôn có xác nhận trước khi chạy. Không giống docker compose down -v gõ tay: Workspace Manager kiểm tra ownership trước khi xoá, chỉ đụng đúng sandbox đó, không đụng sandbox khác.
BASELINE WAIVER

Baseline failure là gì?

Một baseline failure là lỗi test đã tồn tại từ trước khi Task này thay đổi bất kỳ gì — chứng minh được bằng cách chạy lại đúng test đó trên commit gốc (base commit) sạch, không phải chỉ "nhìn có vẻ không liên quan".

Mỗi lỗi khi mới thấy đều mặc định là UNKNOWN. Chỉ khi bấm Reproduce on Baseline và lỗi thật sự lặp lại y hệt (cùng fingerprint) trên base commit, nó mới chuyển thành VERIFIED BASELINE — không bao giờ tự suy đoán.

Khi đó mới có thể Waive Baseline Failure: waiver KHÔNG đánh dấu test PASS — nó chỉ ghi nhận công khai "lỗi này có từ trước, cho Task này đi tiếp" (PASS_WITH_APPROVED_BASELINE_WAIVER), có audit đầy đủ (ai duyệt, lúc nào, lý do). Nếu lỗi thay đổi (fingerprint khác) hoặc là lỗi hoàn toàn mới, waiver không áp dụng được — vẫn phải sửa.

MERGE

PR/Merge thật hoạt động thế nào?

Ở bước Sẵn sàng merge, mỗi repository bắt buộc có một thẻ merge riêng:

  • Repo có GitHub remote (đăng nhập qua gh auth status): Create PR tạo Pull Request thật từ đúng branch đã verify (Integration branch nếu Workflow yêu cầu, hoặc branch của Builder). Không tạo PR trùng — nếu đã có PR cho đúng head/base, dùng lại PR đó.
  • Merge chỉ bật khi: PR đang OPEN, CI không FAIL/PENDING, mergeability CLEAN, source chưa đổi kể từ lúc verify. Bấm Merge sẽ kiểm tra lại toàn bộ (fetch PR mới nhất) ngay trước khi gọi API merge thật của GitHub — không bao giờ tin trạng thái cũ trên màn hình.
  • Conflict: không bao giờ ép merge. Hiện nút Open Integrator để giải quyết xung đột (merge target mới nhất, chạy lại test, push lại).
  • Repo không có GitHub remote: dùng Confirm External Merge (mục "Xem tất cả chi tiết kỹ thuật" → Merge Tracking) — hệ thống kiểm tra thật commit đã verify có nằm trong target branch không trước khi ghi nhận MERGED, bắt buộc nhập lý do, có audit.

Task chỉ DONE khi mọi repository bắt buộc đều MERGED thật — không có nút "Mark All Merged" giả trạng thái nữa.

INTEGRATION

Push Integration Branch dùng khi nào?

Sau khi Integration Merge Latest Changes hoặc resolve conflict, HEAD local của Integration branch thay đổi. Nút Push Integration Branch đẩy đúng branch đó lên GitHub (không force, không branch khác, không remote khác) để cập nhật PR hiện có và kích hoạt CI chạy lại.

Push ≠ Merge. Push chỉ cập nhật branch/PR nguồn trên GitHub — không tự merge, không tự tạo PR mới nếu đã có PR cho branch đó (chỉ refresh PR cũ: cùng số PR, head SHA mới, CI/mergeability refresh lại).

Nút bị disable kèm lý do cụ thể khi: worktree còn thay đổi chưa commit, Integration đang conflict, repo không có GitHub remote, hoặc HEAD hiện tại đã push rồi (không có gì mới để đẩy).

Nếu remote đã đổi từ lần đồng bộ trước (người khác push, hoặc lịch sử phân kỳ), Workspace Manager không bao giờ force-push — hiện PUSH_BLOCKED_REMOTE_CHANGED và yêu cầu vào Integrator giải quyết trước.

BẮT ĐẦU NHANH

Bắt đầu nhanh (chi tiết kỹ thuật)

Toàn bộ vòng đời một task, từ lúc tạo tới lúc sandbox được dọn dẹp. Task chỉ có 6 trạng thái (BACKLOG/ACTIVE/BLOCKED/READY_FOR_MAIN/DONE/CANCELLED) — mọi bước bên dưới (Development/Review/QA/Integration/Merging) là Task Stage, tính tự động, không phải trạng thái riêng lưu trong DB:

  1. Add to BacklogMột ý định công việc — chưa tạo branch/worktree/sandbox nào cả, kể cả khi Task đã có risk profile/brief.
  2. Select for DevelopmentBACKLOG → ACTIVE. Stage vẫn là PLANNING, vẫn chưa cấp resource nào tới khi có Builder Workspace đầu tiên.
  3. Viết Implementation PromptMột prompt tự nhiên, không cần điền GOAL/REQUIREMENTS/ACCEPTANCE_CRITERIA riêng từng ô. Workspace Manager tự sinh AGENT PROMPT (prompt của bạn + context + rule của repo) để review trước khi agent chạy. Sửa prompt sau khi đã có Review PASS sẽ làm review đó STALE.
  4. Create Builder WorkspaceChọn repository, agent, role, sandbox — lúc này mới tạo branch/worktree. Một Task có thể có nhiều Builder Workspace (nhiều repo).
  5. Mở Claude / Codex (desktop hoặc Open in Web)Agent sửa code trong source riêng.
  6. Submit for ReviewAgent Report (WHAT_CHANGED/FILES_CHANGED/TESTS_RUN/HOW_TO_VERIFY) + git worktree sạch — workspace chuyển READY_FOR_REVIEW, ghim đúng commit hiện tại.
  7. Start ReviewMặc định là READ_ONLY review session, không tạo worktree mới. Prompt review tự sinh từ Brief + Agent Report, ghim đúng commit đang review.
  8. PASS / FIX_REQUIRED / BLOCKEDFIX_REQUIRED trả Task về Builder (status BLOCKED). Review chỉ còn hợp lệ cho đúng commit đó — commit mới hoặc Brief đổi version sẽ làm nó tự STALE.
  9. QAChỉ bắt buộc khi risk profile = HIGH, và chỉ sau khi mọi Review đã PASS. LOW/NORMAL bỏ qua bước này (hiện NOT_REQUIRED, không phải PASS giả).
  10. Create IntegrationChỉ bắt buộc khi risk profile = NORMAL/HIGH. LOW risk đi thẳng từ Review PASS sang READY_FOR_MAIN.
  11. READY_FOR_MAINĐủ điều kiện để mở Pull Request — tính tự động (TaskDecisionService), không ai gán tay.
  12. PR / CI / MergeTạo GitHub Pull Request cho từng repo, chờ CI PASS, merge trên GitHub, rồi đánh dấu Merged trong Workspace Manager.
  13. DONEChỉ khi mọi repository bắt buộc đã Merged — một PR còn mở ở bất kỳ repo nào cũng giữ Task ở READY_FOR_MAIN/MERGING, chưa DONE.
  14. Close TaskChỉ là timestamp lưu trữ, không phải điều kiện để dọn sandbox — sandbox/worktree/branch cleanup độc lập với Close.
BƯỚC 1

Khi có bug hoặc task mới

Vào Tasks → New Task. Bạn chỉ cần mô tả task trong một prompt. Workspace Manager tự bổ sung context về repo, branch, worktree, sandbox và rule (AGENTS.md/PROJECT.yaml) khi build prompt thật gửi cho agent — bạn không phải điền GOAL/CONTEXT/REQUIREMENTS/ACCEPTANCE_CRITERIA/... từng ô một.

  • Task title
  • Implementation Prompt — mô tả tự nhiên, không bắt buộc theo khuôn mẫu
  • Repository / Agent / Sandbox (bỏ trống = chỉ vào Backlog)
Ví dụ Implementation Prompt

"Update the MESFlow default password. The seeded admin should use the new password. First login must still require password change. Do not affect existing users. Verify in a fresh sandbox that the new password works and old password does not. Run tests, commit, and report how to verify."

Điền Repository + Agent → bấm Create & Start sẽ tạo Task + Builder Workspace đầu tiên trong cùng một lần bấm, bạn không cần tự tạo worktree riêng. Bỏ trống hai ô này → Task chỉ vào Backlog, chưa tạo branch/worktree/sandbox nào, chọn Select for Development sau khi sẵn sàng.

Mở Advanced nếu cần: base branch, role, Workflow (Low/Normal/High — xem chi tiết, mặc định Normal), hoặc + Add another repository để khai báo thêm repo/agent khác ngay trong lúc tạo Task — xem mục Task nhiều repository. Không cần mở Advanced nếu không cần các tuỳ chọn này.

Workspace Manager sẽ tự tạo branch và worktree riêng cho từng agent. Nếu một Builder Workspace tạo lỗi (ví dụ repo chưa đăng ký), Task và các Builder Workspace đã tạo thành công vẫn giữ nguyên — lỗi hiển thị rõ, không tự rollback.

Tiếp theo: Xem Task vừa tạo, mở agent để bắt đầu code.

HỎI ĐÁP

Implementation Prompt có bắt buộc không?

Không. Nếu bạn chỉ cần giao việc nhanh, chỉ cần nhập tên Task.

Ví dụ

Task: Fix lỗi kiosk không gửi sản lượng

Nếu Prompt để trống, agent sẽ nhận chính tiêu đề này làm yêu cầu — Task Detail sẽ hiện rõ Source: Task Title để bạn biết agent đang chạy theo tiêu đề, không phải một prompt chi tiết bạn quên viết. Đây không phải lỗi, và Start Builder không bao giờ bị chặn chỉ vì Implementation Prompt trống.

Với task phức tạp, nên thêm Prompt chi tiết để mô tả:

  • yêu cầu
  • giới hạn
  • cách test
  • kết quả mong đợi

Thêm Prompt chi tiết sau khi Builder đã chạy hoặc đã Review PASS vẫn được — Task Prompt version sẽ tăng lên và mọi Review/QA dựa trên phiên bản cũ tự động hiện STALE, không bao giờ âm thầm coi tiêu đề và prompt chi tiết là cùng một phiên bản.

AGENT WORKSPACE

Agent Workspace là gì?

Mỗi Agent Workspace (Builder Workspace) là một vùng source riêng cho một agent. Claude sửa task A sẽ không sửa trực tiếp vào source đang dùng bởi Codex hoặc main.

Claude
→ branch riêng
→ worktree riêng
Codex
→ branch riêng
→ worktree riêng
MỘT AGENT WORKSPACE = MỘT REPOSITORY + MỘT BRANCH + MỘT WORKTREE

Add Builder Workspace và Start Builder là hai bước khác nhau, đừng nhầm lẫn:

Add Builder Workspace= tạo source riêng. Chỉ cấp phát branch/worktree (và sandbox nếu có) — agent chưa chạy.
Start Builder= bắt đầu chạy agent. Bấm Start Claude / Start Codex để Workspace Manager thực sự mở CLI agent tại đúng worktree đó.

Bạn không cần tự cd tới thư mục worktree. Bấm Start Claude / Start Codex để Workspace Manager mở đúng nơi (xem mục kế tiếp).

HOÀN THÀNH

Khi agent sửa xong

Agent nên:

  1. Sửa code
  2. Chạy test
  3. Review diff
  4. Commit
  5. Báo kết quả

Sau đó bạn điền Agent Report (WORK_STATUS=READY + WHAT_CHANGED/FILES_CHANGED/TESTS_RUN/HOW_TO_VERIFY/EXPECTED_RESULT/RISKS) và lưu — đây chính là Submit for Review. Nút "Mark Ready" một-click cũ không còn trên giao diện: git worktree phải sạch (không có thay đổi chưa commit) và phải có report thật thì mới coi là sẵn sàng để review.

Submit for Review có nghĩa:

Workspace này đã sẵn sàng để Reviewer xem đúng commit đó. Không có nghĩa là code đã Review PASS, đã QA, đã Integration, hay đã vào main.

Tiếp theo: Start Review — reviewer sẽ thấy đúng report và đúng commit bạn vừa ghim.
Đi tới Tasks
READY ≠ XONG

Agent báo READY rồi thì làm gì?

READY ≠ task hoàn tất, và READY ≠ READY_FOR_MAIN. READY chỉ có nghĩa agent coi source đã xong tại một commit cụ thể, sẵn sàng để Reviewer xem — chưa Review PASS, chưa QA, chưa Integration, chưa sẵn sàng lên main.
READY (Submit for Review)
→ Review PASS
→ QA (chỉ HIGH risk)
→ Integration (chỉ NORMAL/HIGH risk)
→ READY_FOR_MAIN

Workspace Detail và Task Detail đều tách rõ bốn giá trị khác nhau: Task Status (BACKLOG/ACTIVE/BLOCKED/READY_FOR_MAIN/DONE/CANCELLED), Workspace Status (CREATED/READY/CLOSED), Sandbox Status, và Test Status — không gộp chung thành một badge. Task Detail có thêm Overview gate checklist (✓/○) giải thích chính xác vì sao chưa READY_FOR_MAIN, và một khối Bước tiếp theo tính tự động (TaskDecisionService) — không đoán, không dùng AI, chỉ theo luật cố định, và không route/template nào khác được tự tính lại giá trị này.

Nếu agent đã báo cáo theo mẫu Agent Completion Report (templates/agent-completion-report.md: WORK_STATUS/WHAT_CHANGED/HOW_TO_VERIFY/EXPECTED_RESULT/TEST_DATA/RISKS), phần Cách kiểm tra trên trang sẽ hiện đúng nội dung đó — nếu agent chưa báo cáo, trang sẽ nói thật: "Agent chưa cung cấp hướng dẫn kiểm tra." thay vì tự bịa ra các bước.

Một Review PASS chỉ hợp lệ cho đúng commit nó review. Agent commit thêm sau khi Review PASS → review đó tự động hiện STALE, phải Start Review lại — không có route/nút nào "giữ" một PASS cũ qua commit mới.

TÍCH HỢP

Create Integration dùng khi nào?

Integration không còn bắt buộc cho mọi Task. Nó chỉ được yêu cầu khi risk profile của Task là NORMAL hoặc HIGH (xem LOW/NORMAL/HIGH) — một Task LOW risk đi thẳng từ Review PASS sang READY_FOR_MAIN, không qua bước này. Bạn vẫn có thể bấm Create Integration thủ công cho một Task LOW risk nếu muốn có môi trường verification riêng, nhưng nó không phải điều kiện bắt buộc.

Khi bắt buộc: chỉ tạo được sau khi mọi Builder Workspace cần thiết đã Submit for Review và Review PASS ở đúng commit hiện tại — "Create Integration" sẽ báo lý do cụ thể nếu chưa đủ điều kiện, không chỉ disable im lặng.

Một repoTask chỉ có một Builder Workspace vẫn có thể dùng Integration để có môi trường verification riêng (một Repo Integration + một Integration Sandbox).

INTEGRATION AGENT

Integration Agent làm gì?

Integration Agent không phải agent viết feature chính. Nó chịu trách nhiệm:

  • Xem diff của các branch
  • Kiểm tra source nào thay đổi
  • Merge
  • Phát hiện conflict
  • Xử lý conflict đơn giản
  • Chạy test
  • Kiểm tra sandbox
  • Báo READY_FOR_MAIN hay FIX_REQUIRED

Bấm Open Integrator để mở Claude/Codex tại môi trường Integration.

CONFLICT

Nếu merge bị conflict

  • Conflict đơn giản: Integration Agent có thể tự xử lý.
  • Conflict logic/API/schema: Integration Agent phải phân tích trước khi sửa.
  • Nếu không chắc: status = FIX_REQUIRED và trả việc về Agent Workspace phù hợp.
Không cần sửa lỗi của Claude trên integration branch nếu lỗi đó thực sự thuộc branch Claude. Quay lại Claude Workspace → sửa → commit mới → Merge Latest.

SO SÁNH

Restart hay Rebuild?

RestartChạy lại cùng sandbox/source hiện có.

Dùng khi: service treo, backend cần restart.
RebuildBuild lại sandbox từ source hiện tại (commit mới nhất).

Dùng khi: agent vừa commit code mới, Docker image cần build lại, source đang SOURCE STALE.

TIẾN ĐỘ

Xem task đã hoàn thiện tới đâu

Đầu trang Task Detail luôn có badge Status / Stage / Risk, và phần Overview ngay bên dưới là gate checklist (✓/○) — mỗi dòng là một điều kiện thật (Brief đủ, mọi Builder Submit for Review, mọi Review PASS, QA nếu cần, Integration nếu cần, không còn blocking finding, mọi repo bắt buộc Merged). Đây là nơi chính để xem task còn thiếu đúng bước nào — không có phần trăm giả, chỉ ✓ hoặc ○ theo trạng thái thật.

Nếu một Builder Workspace đang chặn Task lại (Reviewer yêu cầu FIX_REQUIRED, QA FAIL, hoặc Integration còn conflict), Task Status chuyển BLOCKED và Overview hiện rõ lý do:

Task blocked by:

codex · frontend: reviewer requested changes

TEST READINESS

Task này test được chưa?

Task Detail trả lời trực tiếp câu hỏi này bằng phần Test Readiness trong Overview, suy ra từ trạng thái thật (không phải một cờ lưu riêng):

NOChưa Builder Workspace nào Submit for Review, hoặc đang có blocking finding (FIX_REQUIRED/BLOCKED chưa xử lý).
PARTIALMột số Builder Workspace đã Submit for Review, một số chưa.
YESMọi Builder Workspace cần thiết đã Submit for Review.

Task Detail cũng phân biệt rõ Builder Tests (agent tự chạy trong worktree), Review, QA, Integration Tests, và CI — năm khái niệm tách biệt, không gộp chung thành một "Tests PASS" duy nhất.

KANBAN

Kanban dùng thế nào?

Kanban hiển thị vòng đời Task theo cột — dùng khi bạn muốn nhìn nhanh nhiều task đang ở đâu. Tasks (List) cùng dữ liệu, dạng bảng, tiện lọc/tìm kiếm. Board và List giữ nguyên bộ lọc khi chuyển qua lại.

CộtÝ nghĩa
BacklogTask chưa có Builder Workspace nào (status = BACKLOG)
DevelopmentĐã chọn để làm, đang code hoặc chưa có Builder Workspace nào
Review / QACó Builder chưa Review PASS, hoặc đang chờ QA (HIGH risk)
IntegrationMọi Review (và QA nếu cần) đã PASS, đang chờ/chạy Integration
Ready for MainMọi gate cần thiết đã đạt — sẵn sàng Pull Request
DoneMọi repository bắt buộc đã Merged
BlockedFIX_REQUIRED/BLOCKED/QA FAIL/merge conflict/merge FAILED chưa xử lý
Cột được tính tự động (TaskDecisionService) từ trạng thái Builder Workspace/Review/QA/Integration/MergeRecord thật — không kéo-thả tuỳ ý để bỏ qua điều kiện.
READINESS

READY_FOR_MAIN nghĩa là gì?

Task đã qua mọi gate mà risk profile của nó yêu cầu (xem LOW/NORMAL/HIGH) và có thể đưa sang PR/CI. Cụ thể với risk NORMAL:

  • Task Brief hợp lệ
  • Mọi Builder Workspace bắt buộc đã hoàn thành (Submit for Review)
  • Mọi Review PASS, đúng commit hiện tại, đúng Brief version hiện tại
  • Integration tồn tại, current, healthy, tests PASS
  • Không còn conflict chưa xử lý

HIGH risk yêu cầu thêm QA PASS (current); LOW risk bỏ qua Integration lẫn QA — chỉ cần mọi Review PASS.

Với task nhiều repo: tất cả repository tham gia Integration phải đạt trạng thái tương ứng — xem Task nhiều repository cho cách theo dõi merge riêng từng repo.
READY_FOR_MAIN không có nghĩa là đã merge main.

Nó chỉ có nghĩa Task đã đủ điều kiện để tạo Pull Request. Nếu bất kỳ evidence nào ở trên trở nên cũ (commit mới, Brief đổi version, source Integration di chuyển), READY_FOR_MAIN tự động biến mất và Task quay lại ACTIVE với gate tương ứng cần làm lại — không có route nào giữ nguyên giá trị này thủ công.

SAU MERGE

Sau khi task merge thành công

Sandbox không bị xóa ngay.

MERGED
↓ Retention
↓ mặc định 24 giờ
↓ Auto Cleanup

Giữ lại một thời gian để còn xem logs, runtime, DB sandbox, evidence — nếu vừa merge xong mà phát hiện vấn đề.

Cleanup giữ lại: task history, source commits, test results, audit, integration report.

POLICY

Workflow: Low/Normal/High khác nhau thế nào?

Trên giao diện, trường này hiện tên là Workflow (nằm trong Advanced khi tạo Task — bạn không cần hiểu chi tiết nếu không mở Advanced; mặc định Normal). Nó quyết định những gate nào bắt buộc trước khi Integration:

Lowcode + review. Bỏ qua cả QA lẫn Integration — Review PASS là đủ để READY_FOR_MAIN.
Normalcode + review + integration. Bỏ qua QA. (mặc định)
Highcode + review + QA + integration. Bắt buộc QA trước khi ghép.
Không có một luồng cứng cho mọi Task — Task Detail's Overview gate checklist và Kanban tự thêm/bớt gate QA/Integration tuỳ risk profile. Một gate bị bỏ qua hiện rõ là NOT_REQUIRED, không bao giờ hiện như thể đã PASS.
WEB TERMINAL

Web terminal dùng thế nào?

Mỗi Agent Workspace có thể mở một AgentSession — một PTY thật (không phải log giả) chạy đúng agent CLI (Claude/Codex) trong đúng worktree, xem trực tiếp từ trình duyệt qua WebSocket.

  1. Open in WebTrên Agent Workspace hoặc Task Detail.
  2. Xem output trực tiếpxterm.js render đúng những gì terminal thật in ra.
  3. Gõ lệnh nếu ở chế độ INTERACTIVEVIEW_ONLY chỉ xem, không gửi được phím.
  4. Stop khi xongDừng hẳn tiến trình, không chỉ đóng tab.

Vào Live Agents để xem mọi session đang chạy trên máy này (Task / Agent / Workspace / State / Sandbox / Last activity).

An toàn lệnh: trình duyệt chỉ gửi được workspace_id + chế độ xem — không gửi được cwd, executable, hay flags. Backend luôn tự suy ra lệnh thật từ danh sách agent đã cấu hình sẵn (giống launcher desktop).
Nếu server Workspace Manager khởi động lại, mọi PTY đang chạy trước đó thực sự đã mất — trạng thái sẽ hiện FAILED trung thực, không báo nhầm là RUNNING.
BẢO MẬT

Remote Access Security

Không expose Web Terminal ra Internet công khai, không xác thực. Terminal PTY tương tác có thể thực thi lệnh thật trong worktree thật.

Nếu cần truy cập từ xa, dùng một trong các phương án đã xác thực:

  • Tailscale (mạng riêng, xác thực thiết bị)
  • Cloudflare Access (xác thực trước khi tới app)
  • SSH tunnel / port-forward tới localhost

Workspace Manager tự nó chỉ bind 127.0.0.1 — đây là lớp bảo vệ đầu tiên; lớp xác thực remote access là trách nhiệm của người vận hành.
